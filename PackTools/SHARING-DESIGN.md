# Pack Sharing & Remix — Design Draft

Status: design only, no code. Sits alongside MCP-DESIGN.md (agent tool surface) and PLAYER-LAYER-DESIGN.md (in-client UI). Those two explicitly punted sharing/moderation to "a later doc" — this is that doc. Scope: how a pack gets published, discovered, forked, re-attributed, and kept safe when a stranger's compiled behavior runs on someone else's lot.

## 0. What's already true, unprompted

Two facts already do half the work here, both from `SCHEMA.md`:

- **Packs are plain JSON.** No proprietary binary format to design a sharing container for. Sharing a pack *is* sharing a `.json` file (or a URL to one).
- **`Decompiler.cs` round-trips `.iff` → pack JSON**, inverting the compiler's operand serializers exactly, erroring loud on anything it can't represent. Forking someone's *compiled* object — not just their source JSON — is already one function call away.

MCP-DESIGN.md §4 already sketched the mechanical fork step (`decompile_object` → `create_pack` → re-play nodes). This doc is about everything around that mechanical step: where packs live, how forks stay traceable to origin, what happens when the source updates after you forked it, and who's allowed to run what.

## 1. Prior art — what real UGC ecosystems did, named

### The Sims / TSO's own modding community (2000s–present, ModTheSims, custom content sites)
The direct ancestor of this project's content, and the closest analog in *spirit* (isometric object mods, no code sandbox — Sims 2/3 mods were literal script injection via `.package` files with no execution boundary). What worked: **naming/attribution culture was social, not technical** — "recolors" and "base meshes" credited by convention (a README-in-the-zip norm), not platform enforcement, and it held up for two decades because the community was small and reputation-based. What broke: zero technical trust model. `.package` mods could and did carry malicious Python/injected DLLs (the Sims 4 modding scene had multiple malware-in-mod incidents); there was never a sandbox, only "download from a site you trust." **Adopt:** attribution-by-convention as a *baseline*, not a substitute for a technical model — this project has more leverage than 2004 ModTheSims did because packs are structured JSON, not opaque binaries, so provenance can be enforced in the format itself instead of hoping authors write a credits file. **Ignore:** "just trust the download site" as a security model — that's the exact failure mode Steam Workshop still has today (see below), and packs here are literally executable game logic, worse than a recolor.

### Steam Workshop
Automatic subscribe/update, one-click "browse → subscribe → it's in your game," ratings/favorites for discovery. What worked: update propagation — subscribing to a mod means you get the author's updates automatically, no manual re-download, which is the right default for "the original updates" question below. What broke badly, and recently: Workshop content for scripting-heavy games (this repo's closest peer — Lua/script-driven mods) has been used as a malware vector because the *scripting layer itself has no sandbox* — a mod's script can shell out, hit the network, touch the filesystem, same trust level as the game binary. The July 2026 "Meccha Chameleon" incidents are exactly this: game scripting interpreters (Lua) executing workshop-supplied code with no restriction on dangerous host calls, exploiting *platform trust*, not a bug. **Adopt:** the subscribe-and-auto-update UX. **Ignore, hard:** unsandboxed script execution — this is the single biggest cautionary tale for this project, because a pack's `trees` are exactly the kind of "user script runs with game-process trust" surface that burned Steam Workshop.

### Minecraft mods (CurseForge / Modrinth)
What worked: **dependency graphs as first-class metadata** — a mod declares what mod IDs/versions it needs, and the platform resolves/warns on missing deps before install. Directly relevant: this project's `clone_from_guid` and future cross-object references are exactly a dependency edge. What worked, part two: **version pinning per mod, not per pack manager** — you can freeze a modpack to specific mod versions so an upstream update doesn't silently break your build. What broke: raw `.jar` mods are full JVM code with no sandbox either (same category as Steam Workshop) — Minecraft's ecosystem safety comes almost entirely from CurseForge/Modrinth's human-and-automated scanning of uploads after the fact, not from any language-level containment. **Adopt:** explicit dependency declarations + version pinning, mapped onto pack `clone_from_guid`/tree-call references. **Ignore:** relying on post-hoc scanning as the *only* safety net — this project can do better because trees aren't arbitrary code, they're a closed vocabulary (see §4).

### Roblox
Closest analog for the "AI-authored, non-programmer creator" angle, and for combined content+behavior review. What worked: review happens on the *published artifact*, and — as of Roblox's March 2026 Safety Snapshot — moderation explicitly targets content that "problematic when combined" even though each individual asset passed its own review ([Fox News](https://www.foxnews.com/tech/roblox-changing-online-safety-ai), [Content Moderation on Roblox – Roblox Support](https://en.help.roblox.com/hc/en-us/articles/21416271342868-Content-Moderation-on-Roblox)). Directly relevant to this project: a gnome pack's dialog strings could each read as fine in isolation but compose into something bad — combination review, not per-field review, is the right target. What worked, part two: Roblox's script sandbox (Luau, capability-scoped, no raw OS calls) — UGC *behavior* has always run inside a real sandbox there, unlike Steam Workshop. That is the load-bearing difference between "safe UGC platform" and "malware vector," and it's a design choice made at the *runtime* level, not the review level. **Adopt:** sandboxed-by-construction behavior execution (this project already half-has this — see §4) and combination-aware content review. **Ignore:** Roblox's scale-driven need for real-time AI moderation of live gameplay — overkill for this project's likely volume; a lighter async review queue suffices at MVP scale.

### Roblox's native capture — real, but not the tiebreaker it first looked like
**Revised after a dedicated verification pass (per Kat) actively hunted for counter-examples — this section previously overclaimed and is corrected below.** Roblox users have captured **930M screenshots and 240M videos in-app**, feeding over 1T cumulative YouTube views — that figure is real and primary-sourced. But the strongest counter-example found on the verification pass is decisive against reading it as a general law: **Nexus Mods has served ~10B mod downloads total, ~6.2B for Skyrim Special Edition alone** (gamesradar.com, destructoid.com, nexusmods.com/skyrim/about/stats) — raw file-download volume driven by the repository itself (browsing, "essential mod list" word-of-mouth, mod-manager tooling), with no comparable video-view number needed or found to explain that scale. The mod file is unambiguously what spreads there, no video required. Roblox itself is more mixed than the earlier framing implied, too: sourcing describes its virality as algorithm + video + community engagement *combined*, not video as the sole or primary driver — in-platform discovery is a co-equal factor, not a footnote. Where the video-first reframe does hold cleanly is TikTok effects, but that's circular: TikTok's discovery surface is *built* video-first on purpose, so of course video is what spreads there. **Sims CC specifically has no data either way** — The Sims Resource (5M+ CC items) and CurseForge (800M+ monthly downloads platform-wide) are self-reported aggregates that don't isolate video-driven downloads from direct-discovery ones.

**Bottom line, corrected: this is format-dependent, not universal — don't generalize "the object doesn't matter, only the video does" into this design.** The original framing below (a pack JSON is a download for a creator; a clip is a shareable moment for everyone else) still holds as a *reason two different mechanics serve two different audiences* — that observation doesn't depend on either one being empirically dominant. But nothing here tells us which one is the bigger lever for *this* product, and the earlier language calling capture "probably the bigger" mechanic (§5, §6) is walked back accordingly. **Adopt, revised:** build native capture as a real, additive sharing surface (§2a) because it's cheap and the Roblox number shows it can matter — not because it's been shown to beat pack publishing. **Do not** treat capture as the priority call for MVP sequencing on the strength of this evidence; §6 downgrades that question from "flagged with a lean" to "genuinely open, no data-driven answer." The in-client-vs-external question for *pack publishing itself* (ModTheSims vs. a Sims 4 Gallery-style in-client registry) remains separately unresolved, as noted before — §2's JSON-only-registry design still stands on its own legal/technical merits (avoiding EA-content redistribution) independent of either virality question.

### Player-invented formats travel further than official content
Worth noting alongside the capture finding: one Sims challenge hashtag has reportedly drawn 1.4M+ posts — a *player-invented format* (a self-imposed ruleset, a naming convention, a "try this and post the result" structure), not anything the platform shipped as content. This is a distribution multiplier orthogonal to both pack-sharing (§2-§3) and native capture (above): a format gives many players a reason to make *comparable* things and post them as a batch, which a registry of arbitrary individual packs doesn't create on its own. Not designing this in fully here — flagged as a §6 open question — but worth naming because it changes what "shareable" should mean: not just "can I publish my pack" but "can the platform make a *format* expressible" (e.g. a pack tagged as part of a challenge, a shared prompt constraint everyone's building against) rather than only ever exposing one-off creations.

### The throughline
The two platforms with a real code-execution surface (Steam Workshop, Roblox) diverge exactly on sandboxing: one has it, one doesn't, and the one without it is having a 2026 malware crisis over it ([techrook.com](https://www.techrook.com/2026/07/how-to-protect-your-pc-from-steam.html), [Pen Test Partners](https://www.pentestpartners.com/security-blog/rating-through-the-steam-workshop/)). This project is structurally closer to Roblox's position than Steam's: **packs are not arbitrary code. They're a closed vocabulary of primitives compiled from a schema that already rejects unknown fields (`SCHEMA.md`, "fail loud").** That is a sandbox already, by construction, not something to bolt on later — the compiler's "unknown fields are a compile error" rule is doing the same job Luau's capability scoping does, just for a much smaller surface. The trust question below is not "can we stop arbitrary code execution" (already mostly solved by the schema being closed) but "can content *within* that closed vocabulary still be griefing, exploitative, or IP-infringing" — that's a review/policy problem, not a sandboxing problem.

## 2. Publish & discover

Borrowing Steam Workshop's subscribe model and Minecraft's dependency metadata, mapped onto this project's actual primitives:

- **A pack is published by submitting its JSON (+ any `appearance.generated` params — no binary assets needed, since art is either cloned by GUID reference or regenerated from params) to a registry.** No new wire format — SCHEMA.md's `pack` object already carries `id`, `name`, `author`, `version`, `description`; publishing adds registry-level fields (`published_at`, `parent_pack_id`/`parent_version` for forks — see §3, `review_status`).
- **Registry is a thin index, not a CDN for compiled `.iff`s.** Ship the JSON; each client compiles locally via the same `FSO.PackCompiler` already in the client's toolchain (per PLAYER-LAYER-DESIGN.md's live-delivery gap — that compile step has to exist client-side anyway). This sidesteps a whole class of "did the registry serve a tampered `.iff`" trust questions for free, and matters more here than in most UGC platforms because of the EA-content posture (STRATEGY.private.md): a pack referencing `clone_from_guid` never contains or transmits EA sprite data, only a GUID reference the *receiving* client resolves against its own self-downloaded base game content. Distributing compiled `.iff`s through a registry would risk redistributing derived EA assets; distributing JSON GUID-references does not.
- **Discovery**: category/tag browse using the schema's existing `category`/`tags` fields (already Buy-Mode-shaped, SCHEMA.md), plus fork-tree browse ("12 remixes of this gnome") once §3's lineage field exists. Ratings/favorites, Workshop-style, are a reasonable v2 — not required for v1 discovery to function.
- **Subscribe = pin a `pack_id`, get updates automatically** when the author republishes a new `version`. This is Workshop's best UX idea and there's no reason not to take it directly.

## 2a. Native capture — the other sharing mechanic, probably the bigger one

Per §1's Roblox-capture finding above: this is a second, separate sharing surface from pack publishing (§2), aimed at a different audience (anyone who wants to show off what their object *did*, not just other creators who want the JSON). Sketch, not a full design — flagged for whoever owns client UI work alongside PLAYER-LAYER-DESIGN.md:

- **Capture the moment, not the object.** A short client-side clip (or screenshot) of an interaction actually happening — the gnome gossiping, the lamp changing color — triggered either by the player (a capture button, Roblox-style) or offered automatically right after a `test_in_vm`/live first-use moment, similar to FIRST-RUN-DESIGN.md §3's "try talking to it" nudge after first placement. That nudge is a natural hook point for a capture prompt specifically, not just a suggestion to interact.
- **The clip carries a reference back to the pack** (`pack_id`/`version`, same lineage field as §3's `forked_from`), so a clip that spreads outside the game still points back to something installable/forkable — this is what makes capture a *funnel into* pack sharing rather than a competing, disconnected feature.
- **No new distribution channel needs designing here for v1** — export-and-share-wherever (save to disk, share via whatever the player already uses) is enough to test whether the loop works at all, matching the "start narrow, prove the mechanic" posture PLAYER-LAYER-DESIGN.md takes toward its own MVP cut. An in-client feed/gallery of captured clips (closer to Roblox's own in-app surface) is a reasonable v2 once there's evidence the capture step itself gets used.

## 3. Forking & attribution

Mechanically, MCP-DESIGN.md §4 already has this: `decompile_object` → `create_pack` → replay. What's missing is what makes a fork *stay* a fork instead of becoming an unlinked copy the moment someone edits it — Minecraft/CurseForge's dependency graph is the model:

- **Every forked pack carries `pack.forked_from: { pack_id, version }` in the JSON itself**, not just registry metadata — so attribution survives a pack being copied outside the registry (someone hands you a `.json` file directly) the same way it survives inside it. This is new relative to MCP-DESIGN.md §4, which left attribution as "just data the agent should preserve" — this makes it a schema field the compiler can validate is present when `create_pack` was seeded from a `decompile_object` result, rather than something the agent has to remember unprompted.
- **`pack.author` stays the fork's own author; `forked_from` carries the lineage.** Same convention as every fork model since ModTheSims' "based on X's mesh" credit line, just structured instead of prose.
- **When the original updates**: the fork does *not* auto-rebase — that's the Minecraft modpack lesson (auto-following upstream silently breaks pinned builds). The registry can *notify* ("the gnome you forked has a new version") and offer a three-way-diff-assisted re-fork, but a fork is a snapshot at fork time, full stop. This avoids a whole class of "my fork broke because upstream changed a tree I never touched" bug reports.
- **Attribution chains, not just parents**: `forked_from` is one hop; the registry can walk the chain for a "remix tree" view, but the schema field itself stays one hop to keep it decompile-and-reattach-safe (a fork of a fork just needs its *own* immediate parent, same pattern recursively).

## 4. Trust & moderation — the load-bearing unsolved piece

Per §1's throughline: the schema's closed vocabulary already gives mechanical safety close to Roblox's Luau sandbox, for free — `SCHEMA.md`'s "unknown fields are a compile error" and PLAYER-LAYER-DESIGN.md §3's existing split (mechanical vs. content safety) both already say this. What's actually open:

1. **Content review, Roblox-combination-aware.** A pack's dialog strings, name, description each look fine reviewed in isolation but the *composition* is what matters (Roblox's March 2026 lesson). Concretely for this schema: review the rendered interaction ("Gossip" action + its dialog table + its `advertised_motives`) as one unit, not field-by-field. This needs an actual review queue and policy — genuinely a product/policy decision Kat should make (who reviews, what's disallowed, is it pre-publish or post-publish-and-flag), not something to guess into this doc.
2. **Resource-exhaustion griefing within the sandbox.** The vocabulary is closed, but "closed" doesn't mean "cheap" — a tree can still `goto_relative` in a loop or push motives/attributes in a tight cycle. `test_in_vm`'s `max_ticks` (MCP-DESIGN.md §3) catches this at author-test time in the harness, but nothing today caps it in a *live shared session* the way it does in the test harness — that's a live-delivery-path gap PLAYER-LAYER-DESIGN.md §4 already flagged generally ("nothing wires compile's output into a running VM"), sharpened here: a shared pack's trees need the same tick/loop ceiling enforced live, not just in the harness, or a malicious/buggy fork can hang someone else's lot.
3. **GUID and namespace collisions across strangers.** SCHEMA.md already reserves a community GUID range and errors on collision *at compile time on one machine*. A registry needs the same guarantee *across every publisher* — a global-uniqueness authority, most simply the registry itself allocating GUIDs on publish rather than trusting client-side allocation (MCP-DESIGN.md §6 already flagged GUID allocation as needing "a real registry/range policy decided at the compiler level" — this is that policy's sharing-side requirement).
4. **IP/content-safety review of AI-generated art**, once `appearance.generated` packs are common (STRATEGY.private.md's replace-EA-content roadmap) — Roblox's own 2026 rollout of AI-asset tooling flagged "IP risk regarding AI-generated assets" as still unresolved industry-wide ([gamineai.com](https://gamineai.com/blog/roblox-ugc-what-game-developers-need-to-know-2026)), so this project inherits an open problem, not a solved one to copy from elsewhere.
5. **Player-side sentiment toward AI-generated content is hostile, and that's a distinct risk from 1-4 — and a follow-up harvest sharpened it from an aggregate stat into a specific, actionable mechanism.** The original finding: **85.4% of surveyed players hold negative views on generative AI content in games** (reported/aggregator-sourced, treat as directional). The follow-up found the variable separating backlash from tolerance isn't "AI vs. no AI" as a binary — it's **disclosure plus visible human authorship**: *Postal: Bullet Paradise* (Dec 2025) was cancelled after an undisclosed AI-generated trailer drew fan backlash, with the developer confirming "extreme damage to our brand" — one named, specific case, not just the aggregate. By contrast, Roblox Code Assist (assists a credited human developer) draws only functional criticism (context-window limits, false-positive bans) and no ethical backlash; Adobe Firefly (3B+ images generated since 2023, plus a "Firefly community tab" keeping human creators visibly credited alongside the tool) draws quality complaints but no boycott. Pattern across all three: AI that assists a visibly-credited human author draws tolerance; AI that produces player-facing finished content *without disclosure* draws boycotts. One cancellation case plus two tolerance cases — a real mechanism worth designing around, not settled law. This sharpens the open question in this doc from "should discovery lead with the player or the AI" into something more specific: **does the discovery/browse UX make it legible that a specific player directed this specific creation** — credit/attribution as a discovery-surface *feature* (something the player sees and the browsing audience sees), not just a `pack.author` field sitting in the JSON (§3). Every pack here is AI-authored by construction (SCHEMA.md), so this project can't opt out of the mechanism by not using AI content — the lever is disclosure-with-credit, not concealment. Still a UX/positioning decision, not a technical one — flagged for Kat, not decided here (see §6).

Items 1, 4, and 5 are policy/positioning calls, not engineering ones — flagging honestly rather than guessing on Kat's behalf. Items 2 and 3 are engineering gaps with a clear direction (live tick-capping; registry-side GUID allocation) but no code yet.

## 5. What's genuinely new vs. borrowed

**Borrowed directly:** Workshop's subscribe/auto-update UX (§2); Minecraft's dependency-declaration and version-pinning pattern, mapped onto `clone_from_guid`/fork lineage (§2, §3); ModTheSims' social attribution convention, upgraded from prose credit to a schema field (§3); Roblox's combination-aware content review target (§4.1) and its sandboxed-behavior-execution posture (§1, §4); Roblox's native in-client capture as *one* additive sharing mechanic (§1, §2a) — real and primary-sourced (930M screenshots / 240M videos), but a verification pass found Nexus Mods' ~10B pure-download volume as a decisive counter-example to reading it as the dominant or universal pattern; treat capture as worth building, not as a proven priority call (see §1's revision, §6).

**New here, not borrowed from anywhere:** remix-by-natural-language is the actual novel piece — every prior-art platform's "fork" means "open the file and edit code/assets by hand." This project's fork means "decompile to JSON, then tell an agent what to change in English, and it re-plays edits through the same `edit_tree_node`/`add_interaction` tools a fresh creation would use" (composes MCP-DESIGN.md §4's mechanical fork step with §1-§2 of MCP-DESIGN.md's authoring loop — no other UGC platform has this because no other platform's mods are LLM-authored from a closed schema in the first place). Also new: shipping JSON-only through the registry and compiling client-side specifically to avoid ever redistributing derived EA sprite data (§2) — a constraint specific to this project's content-ownership posture (STRATEGY.private.md), not something Workshop/CurseForge/Roblox had to solve since their content is either platform-owned or contributor-owned outright.

## 6. Open questions for whoever picks this up next

- **Pre-publish or post-publish-and-flag review?** Pre-publish is safer but adds latency between "player finishes making something" and "it's shareable," which cuts against the whimsy PLAYER-LAYER-DESIGN.md is built around. Product call, not an engineering one.
- **Who reviews at MVP scale** — human queue, LLM-judge pass reusing the same agent stack, or both? Given packs are structured JSON, not free text/video, an LLM-judge pre-pass (flag combinations matching §4.1's pattern, human reviews only flags) seems tractable, but that's a recommendation, not a decision made here.
- **Does the live tick/loop cap (§4.2) live in `FSO.VMHarness` extended for live sessions, or does the live client need its own separate enforcement path?** Depends on how PLAYER-LAYER-DESIGN.md §4's live-delivery gap actually gets closed — that's being designed elsewhere; flagging the dependency rather than guessing at it.
- **Registry-side GUID allocation (§4.3) needs to compose with MCP-DESIGN.md's `add_object` GUID allocation** (currently client/compiler-side) — whoever builds the registry and whoever owns `FSO.PackCompiler`'s GUID range need to agree on one authority, not two.
- **Licensing of forks** — can a fork be re-published under different terms than its parent, can an author mark a pack "no-fork"? Not addressed above at all; pure product/policy, needs Kat's call before the registry's publish flow can be finalized.
- **Relative priority of native capture (§2a) vs. pack publishing (§2) for MVP — genuinely open, not data-driven.** A verification pass found this is format-dependent (Nexus Mods' pure-download-repository model dwarfs anything video-driven at scale; Roblox's own virality is algorithm+video+discovery combined, not video-led) — so there's no evidence-based tiebreaker here, only a structural observation that capture is cheaper to build (no registry, no moderation queue, no GUID-collision policy) if a first, low-cost MVP slice is wanted. This doc doesn't resequence PLAYER-LAYER-DESIGN.md's MVP cut, which currently skips sharing entirely — flagging the sequencing question for Kat without a recommended answer, since the evidence that would have driven one didn't hold up.
- **Whether challenge/format expressibility (§1) is worth designing into the schema or registry at all**, e.g. a lightweight "this pack is part of format X" tag, versus leaving formats as an emergent, ungoverned social behavior the way Sims challenge hashtags are today (no platform mechanism, just convention). Genuinely undesigned here — flagged as a question, not a recommendation, since it's unclear this needs product investment versus happening on its own once capture (§2a) exists.
- **Does the capture nudge (§2a) piggyback on FIRST-RUN-DESIGN.md's "try talking to it" moment, or does that risk overloading one first-success beat with two asks (interact, then also capture)?** Sequencing/UX call for whoever owns that flow, not decided here.
- **How visibly does browse/discovery (§2) credit the human vs. the fact that a pack is AI-authored (§4.5)?** Directly a positioning call given the 85.4%-negative-sentiment finding — "made by [player]" as the primary framing vs. leading with AI-authorship are likely to land very differently with an audience already primed against generative content in games, even for identical objects. Not a technical decision; needs Kat's read on tone before the discovery UI's copy/layout gets finalized.
- **What does "creator" scale actually look like for this registry, and does that change anything about how thin it can stay (§2)?** A separate harvest (reported, aggregator-sourced, not opened at primary source) found active-creator fractions converging near ~1% across structurally different platforms — Roblox (~3.5M/381.8M MAU, ~0.9%) and Scratch, MIT's kids' block-coding platform and arguably the closest "make something from nothing" precedent to this project (~1.4M/130M+ registered, ~1%) — both landing on the general "1% rule" for online communities. Reads as a structural constant, not friction specific to Roblox's or Scratch's toolchain, which raises a real question this doc doesn't answer: does frictionless describe-to-object creation (this project's whole premise, PLAYER-LAYER-DESIGN.md) actually move that 1% floor, or does the floor come from something a better tool can't touch (time, confidence, motivation)? **A follow-up pass actively looked for a counter-example and didn't find one** — checked Canva and TikTok directly for a creator/viewer split; neither publishes one (TikTok reports raw volume, 34M videos/day, not unique-poster fraction; Canva's stats are aggregate only). That doesn't prove the 1% floor is unbeatable, it just means no public evidence beats it anywhere yet — so the tradeoff above stands as flagged, just with less reason to assume better tooling alone moves it, since nobody has shown that happening anywhere. If the floor holds regardless, the registry's discovery/moderation load (§2, §4) may be smaller than a "everyone's a creator now" framing would suggest — worth Kat weighing when scoping how much registry/review infrastructure is worth building ahead of evidence one way or the other.
