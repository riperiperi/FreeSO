# Static Render-Path Verification — Findings

Scope: verify, on disk, that AI-authored packs actually emit the graphics data needed to render — without touching the GUI (a separate session owns the live in-game half of this investigation; see below). Covers the 5 `clone_from_guid` examples in `PackTools/examples/` plus one `appearance.generated` example, as of commit `31aebd64c`.

## 1. Do emitted `.iff` files contain DGRP/SPR2/PALT? — Yes, when the compiler is given a game content directory; no otherwise, and that's mostly by design

Compiled all 5 clone-based examples (`gossip-gnome`, `fortune-cat`, `mood-lamp`, `pet-rock`, `wishing-well`) via `FSO.PackCompiler build`, plus the generated-appearance example (`agentbridge-verify-stool`, chair generator). Read the emitted `.iff`s back for chunk presence.

**Every clone-based example came out with zero DGRP/SPR2/PALT chunks** — `OBJD.BaseGraphicID` stays 0, matching the exact invisible-object failure this investigation was chasing. The generated-appearance example had all three chunk types present.

This is not (mostly) an `AppearanceCloner` bug. `PackTools/FSO.PackCompiler.Tests/AppearanceCloneTests.cs` already covers this precisely and passes:
- `WithoutGameDir_CompilesButEmitsNoGraphics` — confirms the documented, intentional headless-testing behavior (`SCHEMA.md`: compiling without a game dir stays fully functional in the VM, just invisible in-client).
- `WithGameDir_CopiesDrawGroupsAndSpritesInline` — confirms that when a real game content directory *is* supplied, `AppearanceCloner` correctly copies DGRP/SPR2/PALT inline, sets `BaseGraphicID`/`NumGraphics` to a resolvable draw group, and every sprite a draw group references resolves inside the same file.

So the cloning logic itself works. **The actual bug is upstream: the bare CLI never had a way to supply a game content directory to `build` in the first place.** `FSO.PackCompiler/Program.cs`'s `build` case calls `PackCompilerApi.Build(packPath, outDir)` — two arguments, no `gameDir`, no `--game-dir` flag, and no environment-variable fallback anywhere in `FSO.PackCompiler`. `SCHEMA.md` documents `FSO_VM_GAME_LOCATION` as a way to supply it, but that env var is read only by `FSO.ModServer` (`GameContent.cs`, `PackToolHandlers.cs`, `VmHarnessRunner.cs`) and the test suite — never by the compiler CLI itself. Running `FSO.PackCompiler build examples/gossip-gnome.json -o out` with `FSO_VM_GAME_LOCATION` set produces a spriteless object regardless, because the CLI silently ignores the env var it doesn't read. This is a doc/code mismatch worth fixing (either wire `build` to read the env var, or correct `SCHEMA.md` to stop implying it does) — not fixed in this pass, since it's outside the scope handed to this session (static verification + the `install`-specific fix below).

## 2. Are OBJD.BaseGraphicID/NumGraphics set correctly? — Yes, confirmed by the existing test suite

`WithGameDir_CopiesDrawGroupsAndSpritesInline` asserts `objd.BaseGraphicID > 0`, `iff.Get<DGRP>(objd.BaseGraphicID)` resolves, and every sprite referenced by a copied draw group resolves via `iff.Get<SPR2>(...)` in the same file. `GeneratedAppearanceTests.ChairGenerator_ProducesDgrpAndSpr2ChunksInline` asserts the same shape for the generated-appearance path. Both pass. No bug found here.

## 3. `catalog_downloads.xml` — the content-directory trap, confirmed real

Confirmed the exact confusion this investigation flagged going in, **including inside the compiler's own code**: `PackBuilder`'s constructor field `GameDir` is the *sprite source* (TSO content dir, e.g. `~/Library/Application Support/The Sims Online/TSOClient`), while `Install(pack, gameDir)`'s method parameter `gameDir` is the *install target* (e.g. `/Applications/FreeSO.app/Contents/MacOS/Content`, where the `.iff` and `catalog_downloads.xml` actually get written). Same name, two different directories, reused within the same class. `FSO.PackCompiler.Program`'s CLI does distinguish them correctly as `--game-dir`/`--tso-dir` with sane defaults (`DefaultGameDir`/`DefaultTsoDir`), so the *install target* half of this was already fine. The *sprite source* half was not: **`install` would proceed and report success even when no TSO content directory was found, printing only `note: no TSO content dir found ... object will be INVISIBLE` — exit code 0.** Fixed in this pass (§5).

## 4. Generated-appearance objects — structurally sound; the previously-fixed palette bug not re-verified pixel-by-pixel

`GeneratedAppearanceTests.cs` (already present, untracked — presumably another lane's in-flight work) passes all 5 of its cases: DGRP/SPR2/PALT all non-empty, every sprite reference resolves in-file, `BaseGraphicID` valid, mutual-exclusion and validation errors (`generator`+`clone_from_guid` together, unknown generator, non-positive params, unknown param fields) all correctly rejected. This gives confidence at the chunk-structure level.

**Not verified in this pass**: actual pixel content of the quantized frames (i.e., whether the "12 frames each quantized separately, only one saved, rest decoding to opaque black" bug the requester described is still fixed at the pixel level, versus just structurally-present-but-wrong). An attempt to inspect frame pixel data directly via a throwaway xunit test crashed the test host outright (exit 137/SIGKILL, reproducible, cause not diagnosed — possibly unrelated to the pixel-decode path itself, since it crashed before even completing `IffFile` construction logging). Given the existing structural tests pass and the described palette bug was reportedly already fixed elsewhere, this is flagged as **residual risk, not a confirmed problem** — worth a targeted pixel-level check by whoever owns `ArtGen`/`SpriteAssembler.cs`, using a safer inspection method than what was tried here.

## 5. Fix applied: `install` now fails loud instead of silently deploying an invisible object

Changed `PackTools/FSO.PackCompiler/PackBuilder.cs`:
- Added `ObjectReport.GraphicsMissing` (bool) — set when a `clone_from_guid` appearance ends up with zero copied draw groups/sprites, whether because no game content directory was supplied at all, **or** because one was supplied and the clone still copied nothing (previously indistinguishable from success; now also a hard `Diagnostics.Error`, unconditionally, in `BuildObject` — "cloned nothing" is never valid even for `build`/`validate`).
- `PackBuilder.Install` now checks every object's `GraphicsMissing` **before** writing anything, and fails the whole install with an error that names both directories explicitly and says what each is for, e.g.: *"No sprite-source directory (the base game/TSO content install, e.g. `~/Library/Application Support/The Sims Online/TSOClient` — NOT the install target `<gameDir>`) was supplied. Pass `--tso-dir <dir>`."* Fail-loud means fail-*before*-write here: if this fires, no `.iff` and no `catalog_downloads.xml` update happen at all — no partial, misleading install.
- Removed the now-dead "note: ... INVISIBLE" console message in `Program.cs`'s `install` case (unreachable under success now that the library itself fails first).
- `Build`/`Validate` are **unchanged** for the "no game dir at all" case — that stays the documented, intentional headless-testing mode. Only the "supplied a dir and still got nothing" case is now a hard error everywhere, and only `install` treats "no dir supplied at all" as hard-fail, since only `install` claims to actually deploy into a playable game.

Two pre-existing tests in `CatalogTests.cs` (`Install_UpsertsCatalogIdempotently`, `Install_CreatesCatalogWhenMissing`) were installing `gossip-gnome.json` — a `clone_from_guid` pack — with no TSO dir, and asserting success; that was exercising exactly the bug this fix removes. Updated both to install a generated-appearance variant instead, since their actual concern (catalog upsert/write logic) has nothing to do with sprite cloning. Added `InstallTests.cs` covering the new behavior directly: no-tso-dir clone install fails loud and writes nothing, generated-appearance install still succeeds with no game dir needed, and a real-tso-dir clone install still succeeds when content is available (skips gracefully otherwise, same pattern as `AppearanceCloneTests`).

All 50 tests in `FSO.PackCompiler.Tests` and all 42 in `FSO.ModServer.Tests` pass, both with and without a real TSO content directory present.

## 6. What this does and doesn't prove

This confirms the *compiled artifact* is graphically complete when the compiler is fed real game content, and that the specific silent-failure mode this project has hit twice (compiles clean, reports success, renders as nothing) had a real, reproducible instance in the `install` path — now closed. It does **not** prove an object renders on screen; that requires the live in-game half of this investigation (GUI-driving), explicitly owned by a separate, already-in-progress session, and deliberately not attempted here to avoid contending for the same window/process.

One more thing worth carrying forward for whoever picks up the live half: this repo's own in-progress .NET8 client port has the *client* building and reaching its login screen, but core server pieces (`FSO.Server`, `.Database`, `.Domain`, `.Framework`) are still legacy .NET Framework, not Mac-buildable. If the live-render attempt is going through this repo's WIP client rather than the separately-installed `/Applications/FreeSO.app` release build, reaching a lot at all may be blocked on server porting — a different, unrelated lane — not on anything in this findings note. Worth ruling out before diagnosing a render bug that's actually a "can't reach a lot" bug.
